It took Qwen 55,497 tokens to write one letter.

Someone compiled a tiny computer into the weights of Qwen3.5-2B (qwenGPU). Every token the model writes is one step of that machine. I wrote GPU code for it and ran a small neural network on it: a 5,296-parameter transformer that makes up names. This is how.

the real token stream, as Qwen wrote it0 / 55,497

Red EXEC starts a block of instructions. The tokens after it are the values the block computed. It ran for 1 h 43 min on a MacBook and printed z. Every token was compared with a reference simulator, and none was wrong.

The computer inside the model

The machine is tiny: 4 cores, 126 words of memory, 15 registers, 32-bit integers only. No floating point. No division. It does one multiply per step, and it can only shift by numbers known before the program starts.

Its memory lives in the internal state of 45 Gated DeltaNet layers. That is a matrix each layer keeps and overwrites token by token, which makes a good RAM. The machine's weights are compiled by hand, not learned. Qwen's own language layers were removed so the model fits in 16 GB.

Programs are written in CUDA, compiled to PTX by clang, then lowered by qwenGPU into blocks of instructions. The host feeds the program in as tokens, and the model writes out the execution.

A transformer in 33 kernel launches

The name generator has 2 layers, 16 dimensions and 2 attention heads. I trained it on 32,000 names, then converted every weight to an 8-bit integer. The loss went from 2.087 to 2.090.

126 words of memory can't hold the model, so the host streams it in, like cudaMemcpy around every kernel. Each launch gets one 64-word tile of weights plus its inputs, and the host reads the outputs back. One letter takes 33 launches:

Fitting a matrix multiply in 126 words

This is memory during one launch, the second half of a layer's MLP. 64 words of weights (8 rows × 32 inputs, 4 int8 per word), the 32 inputs packed into 16 words, the 16 outputs, and one word for the sum of squares the next RMSNorm needs.

Two multiplies for the price of one

The machine does one multiply per step, and a matrix multiply is nothing but multiplies. So the kernel packs two 8-bit weights into one 32-bit word, and two inputs into another, in opposite order. One 32-bit multiply then leaves a₀·x₀ + a₂·x₂ sitting in the top 16 bits, exactly. Try it:

The cross terms land in the bottom half and above bit 32, where they fall off. A word of four weights costs 5 multiplier operations instead of 12.

Hand-ordering the instructions

The machine runs instructions in blocks of 4 stages: logic in stage 1, the multiply in stage 2, memory atomics in stage 3. The compiler packs instructions into blocks greedily, in the order it gets them. Clang's order wasted half of every block, so the inner loop of the matrix multiply is hand-written PTX, ordered so each block is full:

// one weight word: 5 blocks instead of 10. Each line: stage 1 | stage 2 | ...
ld w      | and e = w & 0x00FF00FF  | mul.hi t = w >> 8  | sub ew = e - 0x00800080
ld ex     | and o = t & 0x00FF00FF  | mul m1 = ew * ex     | add l1 = m1 + 0x80008000
ld ox     | sub ow = o - 0x00800080  | mul m2 = ow * ox     | add l2 = m2 + 0x80008000
          |                         | mul.hi h1 = l1 >> 16 | add acc += h1
          |                         | mul.hi h2 = l2 >> 16 | add acc += h2

There's no shift by a variable either, so x >> 8 is written as mulhi(x, 2²⁴): multiply, keep the top half.

exp() without floats

Softmax and SiLU need e−x. There are no floats, but e−x is the limit of (1 − x/n)n. With n = 1024 = 2¹⁰, that's one subtraction and then ten squarings, in 30-bit fixed point.

Division without a divider

Softmax has to divide by the sum, and sigmoid is 1/(1 + e−x). The machine can't divide by a value computed at run time, so 1/d is Newton's method: guess, then repeat y ← y·(2 − d·y). Each step doubles the correct digits. Starting from the straight line 24/17 − 8/17·d, three steps are enough for every d in [1, 2).

Square root, one bit at a time

RMSNorm divides by √(mean of squares). Instead of a square root, the kernel finds the largest r with r²·Σx² below a threshold, setting one bit per step from the top: 15 steps, exact, no rounding.

The sum Σx² comes for free: every kernel that writes the residual stream also atomicAdds each value squared into one word. That removed a whole launch per norm.

A bug in the compiler

The first argmax always returned 0. For best = max(v, best); idx = v > best ? k : idx, clang emits a compare, then the max, then a select. qwenGPU's compiler recomputes the compare right next to the select, because conditions can't cross blocks. By then the max has already overwritten best, so the condition is always false.

setp p, v, best        // p = v > best
max  best, v, best     // best overwritten
selp idx, k, idx, p    // the compiler re-checks v > best here: always false

On [3, 1, 4, 1, 5, 9, 2, 6], the PTX interpreter returns 5 and the compiled blocks return 0. The sample kernel works around it, and there's a repro in the repo.

Did it work?

Inside Qwen, the model wrote 55,497 tokens for one letter, and every one matched the simulator. The output buffers of all 33 launches matched a plain numpy version of the model, bit for bit. The letter was z, the same as numpy's.

At 9 tokens a second, a whole name inside Qwen takes most of a day. So the full names ran on the simulator, the same machine in Python. 20 names and 4,587 launches, all identical to numpy:
